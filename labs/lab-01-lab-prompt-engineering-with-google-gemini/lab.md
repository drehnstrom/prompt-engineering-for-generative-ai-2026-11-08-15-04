# Prompt Engineering with Google Gemini

## Time Required

30 minutes

## Overview

In this lab, you will practice core prompt engineering techniques using Google Gemini. You will progress from diagnosing why underspecified prompts fail to building structured multi-component prompts, directing output depth with personas, enforcing strict JSON output schemas, guiding edge-case handling with few-shot exemplars, and iteratively refining prompts against noisy real-world data.

### You learn how to:
- Construct structured prompts using explicit role, context, task, constraints, and format components.
- Apply distinct professional personas to calibrate tone and technical depth for different audiences.
- Enforce strict output constraints and JSON schemas without conversational filler.
- Build few-shot exemplars to standardize classification and formatting behavior.
- Diagnose prompt failure modes and iteratively refine instructions against noisy inputs.

## Scenario

Your engineering team is adopting Google Gemini to automate incident communications, extract action items from meeting notes, and triage customer support tickets. Initial tests produced inconsistent outputs: some responses included conversational pleasantries, others leaked internal hostnames to customer drafts, and several failed to parse as valid JSON. You have been tasked with establishing reliable, production-ready prompts that eliminate model guesswork and deliver consistent results.

## Lab Instructions

### Task 1: Access Google Gemini and construct a structured prompt

In this task, you open Google Gemini and compare an underspecified prompt with a structured multi-component prompt.

1. Open your web browser and navigate to [Google Gemini](https://gemini.google.com/).

2. Sign in using your Google account.

3. To observe how an underspecified request forces the model to guess tone and audience, enter the following prompt in the chat box:

```text
Write an update on the project delay.
```

> [!NOTE]
> Notice how Gemini invents reasons for the delay, guesses who will read the update, and produces generic prose that requires substantial editing before anyone can send it.

4. Clear the chat or start a new chat session by clicking **New chat** in the left navigation panel.

5. To provide clear boundaries and eliminate guesswork, enter the structured prompt below:

```text
Role: You are a technical documentation lead at a cloud software company.
Task: Summarize the incident notes below into a customer-facing status update.
Audience: Enterprise customers affected by the service disruption.
Constraints:
- Keep the total response under 120 words.
- Do not mention internal server hostnames or engineer names.
- Use a calm, reassuring, and professional tone.
Format: A single paragraph followed by two bullet points for next steps.

Incident Notes:
Database cluster db-prod-04 experienced memory exhaustion at 14:10 UTC.
Lead engineer Sarah initiated failover to db-prod-05 at 14:18 UTC.
Failover completed at 14:28 UTC. Normal query latency restored.
Engineers are reviewing cache eviction policies to prevent recurrence.
```

6. Review the output generated by Gemini.

> [!IMPORTANT]
> Verify that the output adheres to your constraints: it must omit internal hostnames like `db-prod-04` and employee names like `Sarah`, stay under 120 words, and match the single-paragraph plus two-bullet structure.

### Task 2: Calibrate tone and technical depth using personas

In this task, you assign two contrasting professional personas to the same incident data to evaluate how role framing anchors vocabulary, technical depth, and strategic focus.

1. Start a new chat session in Google Gemini.

2. To generate an executive-level summary, enter the following prompt assigning a Chief Information Security Officer persona:

```text
Role: You are a Chief Information Security Officer (CISO) briefing the Board of Directors.
Task: Explain the business impact of the security incident described below and provide executive recommendations.
Audience: Corporate board members with financial and governance oversight, but limited hands-on technical knowledge.
Constraints:
- Focus on business continuity, compliance risk, and mitigation budget.
- Omit raw command syntax, server ports, and low-level packet logs.
- Provide exactly three strategic action items.
Format: An executive summary paragraph followed by three numbered action items.

Incident Data:
At 03:15 UTC, unauthorized API calls targeted endpoint /api/v1/export using an exposed service account token.
Approximately 4,200 non-sensitive customer profile records were accessed before rate-limiting triggered at 03:22 UTC.
Token was revoked at 03:30 UTC. Audit logs confirm no payment details or passwords were exposed.
Mandatory breach reporting threshold under applicable privacy regulations is under legal review.
```

3. Review the response and observe how the CISO persona prioritizes enterprise risk, regulatory reporting, and board-level governance.

4. In the same chat or a new chat session, submit the same incident data with a Lead Security Engineer persona:

```text
Role: You are a Lead Application Security Engineer writing an internal post-mortem ticket for backend developers.
Task: Analyze the technical root cause of the incident below and specify engineering remediation steps.
Audience: Senior backend and DevOps engineers responsible for API gateway security.
Constraints:
- Focus on authentication controls, secret rotation pipelines, and automated detection rules.
- Use precise technical terminology (e.g., IAM policies, token entropy, audit logging).
- Provide concrete implementation steps.
Format: A technical analysis paragraph followed by three bulleted engineering tasks.

Incident Data:
At 03:15 UTC, unauthorized API calls targeted endpoint /api/v1/export using an exposed service account token.
Approximately 4,200 non-sensitive customer profile records were accessed before rate-limiting triggered at 03:22 UTC.
Token was revoked at 03:30 UTC. Audit logs confirm no payment details or passwords were exposed.
Mandatory breach reporting threshold under applicable privacy regulations is under legal review.
```

5. Compare the two responses side by side.

> [!TIP]
> Notice how both prompts used identical incident data, yet the persona directed Gemini to highlight business liability for board members and API gateway controls for developers.

### Task 3: Enforce constraints and structured output schemas

In this task, you extract unstructured meeting notes into an exact JSON schema while applying negative constraints to prevent formatting leaks.

1. Start a new chat session in Google Gemini.

2. To test schema extraction without negative constraints, enter the following prompt:

```text
Extract the action items from this meeting note:
Project sync on Tuesday: Marcus will patch the staging Kubernetes cluster by Friday.
Elena agreed to draft the customer communication template by tomorrow at 5 PM.
Database migration script needs review, but no one took ownership yet.
Format as JSON.
```

3. Observe Gemini’s response.

> [!NOTE]
> When asked loosely for JSON, models often prepend conversational text like “Sure! Here is the JSON you requested:” and wrap the output in markdown fences (` ```json `). In automated pipelines, this conversational text causes JSON parsing errors.

4. To enforce strict schema compliance and eliminate conversational filler, enter the refined prompt below:

```text
Task: Extract all action items from the meeting transcript into structured JSON.

Output format rules:
- Return valid JSON only.
- Do not include markdown code fences, backticks, or introductory conversational text.
- Do not include closing commentary or explanations.
- Follow this exact schema:
{
  "tasks": [
    {
      "task_id": 1,
      "description": "Short summary of action item",
      "owner": "Person responsible or 'Unassigned'",
      "due_date": "YYYY-MM-DD, specific time, or 'TBD'"
    }
  ]
}

Meeting Transcript:
Project sync on Tuesday: Marcus will patch the staging Kubernetes cluster by Friday.
Elena agreed to draft the customer communication template by tomorrow at 5 PM.
Database migration script needs review, but no one took ownership yet.
```

5. Examine the output. Verify that every task was captured, the unassigned migration script was marked as `Unassigned`, and no conversational pleasantries surrounded the JSON block.

### Task 4: Guide model behavior with few-shot exemplars

In this task, you use few-shot prompting to guide Gemini to classify customer support tickets into a standardized, pipe-delimited schema with consistent urgency ratings.

1. Start a new chat session in Google Gemini.

2. To see how zero-shot classification produces inconsistent styling, enter:

```text
Classify this support ticket by category, urgency, and action:
"Credit card charged twice for annual subscription renewal."
```

3. Note that the zero-shot response may format the result as bullet points, a multi-paragraph explanation, or arbitrary category labels.

4. To anchor the exact classification vocabulary and format, provide three consistent input-output exemplars followed by the target input:

```text
Classify customer support tickets into Category, Urgency, and Action.
Use only the following categories: Hardware, Authentication, Billing, Feature Request.
Use only the following urgencies: Low, Medium, High, Critical.
Follow the exact single-line pipe-delimited format demonstrated in the examples.

Input: "My screen goes blank whenever I unplug the HDMI cable."
Output: Category: Hardware | Urgency: Medium | Action: Replace cable or adapter

Input: "Cannot log into production portal. Entire sales team is locked out."
Output: Category: Authentication | Urgency: Critical | Action: Reset tenant session

Input: "Would love to see a dark mode option in the next mobile release."
Output: Category: Feature Request | Urgency: Low | Action: Log to backlog

Input: "Credit card charged twice for annual subscription renewal."
Output:
```

5. Confirm that Gemini completes the pattern with an output matching the exemplars:

```text
Category: Billing | Urgency: High | Action: Issue refund or verify duplicate transaction
```

> [!NOTE]
> The exemplars taught Gemini three things simultaneously: allowed category values, allowable urgency levels, and the single-line pipe-delimited syntax, all without requiring paragraphs of explanatory rules.

### Task 5: Diagnose failures and iteratively refine prompts

In this task, you test a prompt against noisy, unverified data and iteratively apply constraints and delimiters to fix hallucinations and scope creep.

1. Start a new chat session in Google Gemini.

2. To establish a baseline on noisy input text, enter the following prompt:

```text
Summarize the key facts from these field notes:

Field Notes:
Technician Dave arrived at site Austin-02 at 09:00. Power supply unit PSU-1 was replaced.
Dave thinks the air conditioning in rack 4 might be failing soon, but he didn't check it.
Rumor has it that vendor XYZ makes bad cooling fans anyway.
Server rack 4 ambient temperature was measured at 21 degrees Celsius.
Maintenance completed at 10:15.
```

3. Review the baseline summary. Notice whether Gemini included Dave’s unverified suspicion about the air conditioning or the vendor rumor as if they were established facts.

4. Identify the failure mode: the prompt used an open verb (“Summarize”) without grounding rules or negative constraints, allowing subjective commentary and unverified rumors to enter the summary.

5. To tighten and lock the prompt, apply role boundaries, explicit section delimiters, and strict negative constraints:

```text
Role: You are a data verification specialist auditing data center maintenance records.
Task: Extract verified operational facts from the field notes delimited by triple quotes.

Constraints:
- Include only completed actions, measured readings, and recorded timestamps.
- Explicitly exclude unverified opinions, suspicions, and rumors.
- If an item was not directly measured or performed, do not include it.
- Format the response as a bulleted list with maximum 4 bullets.
- Do not add introductory or concluding remarks.

Field Notes:
"""
Technician Dave arrived at site Austin-02 at 09:00. Power supply unit PSU-1 was replaced.
Dave thinks the air conditioning in rack 4 might be failing soon, but he didn't check it.
Rumor has it that vendor XYZ makes bad cooling fans anyway.
Server rack 4 ambient temperature was measured at 21 degrees Celsius.
Maintenance completed at 10:15.
"""
```

6. Confirm that the refined output extracts only verified operational facts (arrival time, PSU replacement, measured temperature, completion time) and completely drops the unverified rumors.

### Bonus Task 6: Assemble a reusable prompt template

In this bonus task, you synthesize the techniques learned in this lab into a standardized prompt template that teammates can reuse across different generative AI tasks.

1. Review the components required for a production prompt template:
   - System Role or Persona
   - Primary Task Directive
   - Intended Audience
   - Input Data with Delimiters
   - Explicit Constraints (including measurable bounds and negative rules)
   - Target Output Format or Schema
   - Optional Few-Shot Exemplars

2. In Google Gemini, test your reusable template structure using a new scenario of your choice (such as converting raw customer feedback into a product feature request ticket).

```text
Role: [Define profession, seniority, and perspective]
Task: [State primary action clearly]
Audience: [Specify reader's technical depth and business focus]
Constraints:
- [Specify measurable length or count limit]
- [Specify negative constraints: what MUST NOT be included]
- [State grounding rule: restrict output to provided text only]
Format: [Define exact schema, JSON structure, or markdown layout]

Input Data:
"""
[Paste raw input text here]
"""
```

3. Verify that your template consistently produces grounded, structured, and audience-appropriate outputs across multiple test runs.
